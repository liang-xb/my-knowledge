## 缓存更新策略

缓存更新是 Redis 为了节约内存而设计的机制。当向 Redis 插入太多数据时，可能会导致缓存中的数据过多，所以 Redis 会对部分数据进行更新（淘汰）。

- **内存淘汰**：Redis 自动进行，当 Redis 内存达到设定的 max-memory 时，自动触发淘汰机制，淘汰掉一些不重要的数据（可以自己设置策略）
- **超时剔除**：给 Redis 设置过期时间 TTL 后，Redis 会将超时的数据删除
- **主动更新**：手动调用方法删除缓存，通常用于解决缓存和数据库不一致问题

## 数据库与缓存不一致

### 基本解决方案

![解决方案](40.png)

### 方案讨论

综合考虑使用方案一（先更新数据库，再删除缓存）。操作缓存和数据库时有三个问题需要考虑：

- 删除缓存 vs 更新缓存：删除缓存更简单，下次查询时自然加载最新数据
- 先操作数据库还是缓存：先操作数据库，再删除缓存，出现异常的概率较低
- 如何保证两步都成功：可采用消息队列、Canal 等方式保证最终一致性

## 缓存穿透

### 问题描述

缓存穿透是指客户端请求的数据在 **缓存和数据库中都不存在**，这样缓存永远不会生效，这些请求都会打到数据库。

![缓存穿透](41.png)

### 解决方案

**方案一：缓存空对象**

当查询数据不存在时，将 null 也缓存起来，并设置较短的 TTL：

```java
@Cacheable(cacheNames = "user", key = "#id", unless = "#result == null")
public User getById(Long id) {
    User user = userMapper.selectById(id);
    if (user == null) {
        // 缓存空对象解决穿透
        redisTemplate.opsForValue().set("user:" + id, "", 2, TimeUnit.MINUTES);
    }
    return user;
}
```

**方案二：布隆过滤器**

在缓存层之前加一层布隆过滤器，判断数据是否存在，不存在的直接拒绝请求。

## 缓存雪崩

### 问题描述

缓存雪崩是指在同一时段 **大量的缓存 key 同时失效** 或者 **Redis 服务宕机**，导致大量请求直接到达数据库，带来巨大压力。

![缓存雪崩](48.png)

### 解决方案

- 给不同的 key 的 TTL 添加随机值，避免同时过期
- 利用 Redis 集群提高服务的可用性（哨兵、集群）
- 给缓存业务添加降级限流策略（如 Sentinel、Hystrix）
- 给业务添加多级缓存（浏览器缓存 + Nginx 缓存 + Redis 缓存 + JVM 缓存）

## 缓存击穿

### 问题描述

缓存击穿问题也叫 **热点 key 问题**，就是一个被 **高并发访问** 并且 **缓存重建业务较复杂** 的 key 突然失效了，大量的请求会在瞬间给数据库带来巨大的冲击。

![缓存击穿](49.png)

### 解决方案

**方案一：互斥锁**

当缓存失效时，只有拿到锁的线程才能查询数据库并重建缓存，其他线程等待：

```java
public User getById(Long id) {
    String key = "user:" + id;
    String userJson = redisTemplate.opsForValue().get(key);
    if (userJson != null) {
        return JSON.parseObject(userJson, User.class);
    }

    // 获取互斥锁
    String lockKey = "lock:user:" + id;
    try {
        if (redisTemplate.opsForValue().setIfAbsent(lockKey, "1", 10, TimeUnit.SECONDS)) {
            // 双重检查
            userJson = redisTemplate.opsForValue().get(key);
            if (userJson != null) {
                return JSON.parseObject(userJson, User.class);
            }
            // 查数据库
            User user = userMapper.selectById(id);
            redisTemplate.opsForValue().set(key, JSON.toJSONString(user), 30, TimeUnit.MINUTES);
            return user;
        } else {
            Thread.sleep(50);
            return getById(id); // 重试
        }
    } finally {
        redisTemplate.delete(lockKey);
    }
}
```

**方案二：逻辑过期**

不给热点 key 设置 TTL，而是在 value 中记录逻辑过期时间。当发现数据已过期时，先返回旧数据，然后异步重建缓存。
