### RDB 持久化

RDB 全称 Redis Database Backup file（Redis 数据备份文件），也被叫做 Redis 数据快照。简单来说就是把内存中的所有数据都记录到磁盘中。当 Redis 实例故障重启后，从磁盘读取快照文件，恢复数据。快照文件称为 RDB 文件，默认保存在当前运行目录。

RDB 持久化在以下四种情况会执行：

1. 执行 save 命令（同步，会阻塞主进程）
2. 执行 bgsave 命令（异步，fork 子进程执行）
3. Redis 停机时（自动执行 save）
4. 触发 RDB 条件时（配置文件中设置）

```bash
# redis.conf 配置
save 900 1      # 900秒内至少1次修改
save 300 10     # 300秒内至少10次修改
save 60 10000   # 60秒内至少10000次修改
```

**RDB 优点：** 文件紧凑、适合备份和灾难恢复、最大程度恢复数据、不影响主进程

**RDB 缺点：** 两次 RDB 间隙可能丢失数据、fork 子进程会占用内存

### AOF 持久化

AOF 全称 Append Only File（追加文件）。Redis 处理的每一个写命令都会记录在 AOF 文件，可以看作是命令日志文件。

AOF 默认关闭，需要修改配置文件：

```
appendonly yes
appendfilename "appendonly.aof"
```

**AOF 刷盘策略：**

| 配置值 | 刷盘时机 | 说明 |
| ------ | -------- | ---- |
| always | 每条命令 | 最安全，性能最低 |
| everysec | 每秒一次 | 最多丢 1 秒数据（推荐） |
| no | 由操作系统决定 | 不可控 |

**AOF 重写：** AOF 文件会不断增大，Redis 提供 AOF 重写（bgrewriteaof）来压缩文件，只保留恢复数据的最小命令集。

### RDB 与 AOF 对比

| 对比项 | RDB | AOF |
| ------ | --- | --- |
| 持久化方式 | 定时快照 | 记录每次写命令 |
| 数据完整性 | 可能丢失最后一次快照后的数据 | 取决于刷盘策略 |
| 文件大小 | 小（二进制压缩） | 大（记录所有命令） |
| 恢复速度 | 快 | 较慢 |
| 系统资源占用 | 高（fork 子进程） | 低 |
| 使用建议 | 备份和灾难恢复 | 对数据安全性要求高 |

## Redis 主从架构

### 基本介绍

主从架构中，主节点负责写操作，从节点负责读操作，实现读写分离。主节点数据变更会同步给从节点。

**搭建主从：**

```bash
# 从节点配置文件添加
replicaof <masterip> <masterport>

# 或在启动时指定
redis-server --replicaof 192.168.1.100 6379
```

### 主从同步原理

**全量同步：**

1. 从节点请求同步（发送 replid 和 offset）
2. 主节点判断是否需要全量同步（replid 不匹配）
3. 主节点执行 bgsave 生成 RDB 快照
4. 主节点将 RDB 发送给从节点
5. 从节点加载 RDB
6. 主节点将缓冲区的增量命令发送给从节点

**增量同步：**

主节点维护一个 replication backlog buffer，记录所有写命令。从节点断线重连后，通过 offset 判断是否需要增量同步。

## Redis 哨兵模式

### 基本介绍

哨兵（Sentinel）是 Redis 的高可用方案，用于监控主从节点状态，在主节点故障时自动选举新的主节点。

![哨兵架构](90.png)

**哨兵的作用：**

- **监控**：持续监控主从节点是否正常
- **自动故障转移**：主节点故障时，自动选举新主节点
- **通知**：将故障转移结果通知客户端

### 哨兵配置

```bash
# sentinel.conf
sentinel monitor mymaster 192.168.1.100 6379 2
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 10000
```

- `mymaster`：主节点别名
- `2`：至少 2 个哨兵认为主节点故障才触发故障转移（客观下线）
- `down-after-milliseconds`：哨兵 ping 超时时间
- `failover-timeout`：故障转移超时时间

## Redis 集群模式

### 为什么需要集群

单节点 Redis 存在以下问题：

- 并发能力有限（单节点 QPS 上限约 10 万）
- 数据量有限（受限于单机内存）
- 单点故障风险

### 分片集群

Redis Cluster 将数据分散存储在多个 Redis 节点上，每个节点存储一部分数据。采用 **哈希槽（Hash Slot）** 机制，共 16384 个槽位。

```bash
# 创建集群
redis-cli --cluster create 192.168.1.101:6379 192.168.1.102:6379 \
    192.168.1.103:6379 192.168.1.104:6379 \
    192.168.1.105:6379 192.168.1.106:6379 \
    --cluster-replicas 1
```

**集群特点：**

- 数据分片存储，每个节点存储一部分数据
- 每个分片都有主从结构，保证高可用
- 客户端可以连接任意节点，自动路由到正确节点
- 支持动态扩缩容（reshard）

**哈希槽计算：** `slot = CRC16(key) % 16384`
